# Throughput and latency (metrics)

- Tag: structure

## Definition

- **Throughput**: number of completed jobs per unit time.
- **Latency**: time to complete a job (often treated as worst-case or tail in practice).

## Scope note

These are core performance metrics used to evaluate and trade off system behavior; analysis often distinguishes **global** measures (end-to-end) from **local** measures (component-level).

Latency is often the most directly actionable metric for quantifying impact and estimating potential speedup when time can be decomposed into contributing waits.

Because “latency” can be measured at different points and for different operations, it is best treated as a qualified measurement (e.g., request latency, connection latency) rather than a standalone label.

Many subsystems couple the same knob to both dimensions (e.g., batching/coalescing or larger transfer units that raise throughput while adding latency to individual units of work), so “optimize latency” and “optimize throughput” are not always separable without redesign.

When a dashboard “latency” does not match user-perceived latency, suspect a **definition or scope mismatch** before rewriting code ([[measurement-validity]]).

**CPU utilization** is not a latency metric: it is at best a **component-local throughput / busy proxy**. Treat it as comparable across hosts or windows only when **semantics and scope** are explicit (what counts as “busy,” per-CPU vs aggregate, guest vs host, quota vs socket)—see [[measurement-validity]].
